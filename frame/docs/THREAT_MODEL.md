# Accnary 威胁模型与安全说明

版本：2026-10-27（在 Phase 4 自验收基础上补充更新链路边界）
适用：Accnary 0.1.0（Windows，本地单用户）

## 1. 资产与信任边界

**核心资产**：密码库文件（KDBX 4.0）内的全部凭据 —— 账户密码、登录方式、
微信/QQ/手机号/邮箱身份、付费授权激活码、自定义字段（可能存放 API Token
与恢复码）、条目历史与附件。

**信任边界**：

```
┌─ 用户机器（受信边界内，但假设可能被恶意软件部分窥视）────────────┐
│  Accnary 进程（Python + PySide6）                               │
│    内存：主密码、解密后的目录、搜索索引（明文元数据）              │
│    磁盘：唯一权威库文件（AES-256 + Argon2d）+ .bak 快照（同样加密）│
│    剪贴板：复制后的明文凭据（30 秒条件清除）                       │
│    配置：%APPDATA%\Accnary\Accnary.ini（路径/主题/偏好，无凭据）   │
└──────────────────────────────────────────────────────────────────┘
        ↑↓ 本地文件读写
   外部：U 盘/云盘同步的库文件副本、KeePassXC 等第三方工具
```

Accnary 不监听端口、不做云同步或遥测。启用更新检查时，仅通过 HTTPS 读取 ToolHub
清单；只有用户确认更新后才下载程序 EXE，并校验 SHA-256。更新请求不包含密码库路径、
主密码、账号数据或使用记录，也不会修改 KDBX、加密备份或 `.lock` 文件。

## 2. STRIDE 分析与对策

| 威胁 | 场景 | 对策 | 残余风险 |
|---|---|---|---|
| **S** 伪造 | 恶意 .kdbx 冒充合法库 | KDBX 头部 SHA-256 + HMAC 双校验；篡改即 `VaultFormatError` 干净拒识，不做"修复" | 无已知绕过 |
| **T** 篡改 | 磁盘上库文件被第三方改写 | 保存前 SHA-256 冲突检测（`ConflictError`），绝不静默覆盖；每次安全保存前保留加密快照 `.bak` | TOCTOU 窗口（毫秒级，见 §4） |
| **R** 抵赖 | — | 单用户本地工具，不适用 | — |
| **I** 信息泄露（磁盘） | 库文件/备份/临时文件被拷走 | 全部落盘文件均为 KDBX 加密（含 .bak/.pre-restore.bak/临时文件）；不创建任何明文中间文件（自动化泄露测试验证）；配置 INI 无凭据 | 若主密码弱，离线爆破可行 —— 主密码强度是第一道防线 |
| **I** 信息泄露（内存） | 恶意软件读进程内存；休眠文件/内存转储 | 尽量减少明文副本与生命周期；锁定即丢引用 | **Python 无法保证彻底擦除所有字符串副本**（不宣称内存清除）。本地恶意软件如果已能读内存，通常也能装键盘记录器 —— 这类攻击者面前所有本地密码管理器同等受限 |
| **I** 信息泄露（剪贴板） | 复制的密码被其他程序/剪贴板历史读取 | 30 秒条件清除（不覆盖用户新复制内容）；UI 提示 | Windows 剪贴板历史（Win+V）与云剪贴板可能在清除前已捕获；用户可关闭系统剪贴板历史 |
| **I** 信息泄露（搜索索引） | 锁定后索引残留明文元数据 | 索引纯内存且锁定即清空；敏感值（密码/激活码/字段值）从不入索引（测试断言） | — |
| **D** 拒绝服务 | 库文件损坏/磁盘满/权限异常 | 临时文件 + 重开验证 + 原子替换；任一步失败保留上一版本（故障注入测试覆盖）；打开时自动清理遗留临时文件 | 磁盘级灾难需靠外部备份 |
| **E** 提权 | — | 程序不需要管理员权限；不写注册表（配置为 APPDATA INI）；不修改系统/其他软件 | — |

## 3. 明确不做的事（设计承诺）

- 无云同步、无遥测、不访问账号网址、不下载头像；更新检查仅访问 ToolHub，下载与安装须用户确认；
- 不调用 DPAPI 或任何替代主密码的机制；
- 不自动填充浏览器/其他应用；
- 模糊搜索结果不用于任何自动授权（仅人工查看）；
- 未经用户明确确认不覆盖已存在文件、不恢复备份。

## 4. 已知残余风险（用户必须知情）

| # | 风险 | 等级 | 缓解建议 |
|---|---|---|---|
| R1 | Python 运行时无法保证彻底擦除内存中的明文凭据 | 接受（行业共性） | 主密码要长且唯一；不在不信任的机器上解锁 |
| R2 | 剪贴板历史/其他剪贴板管理器可截获复制内容 | 中 | 系统设置关闭剪贴板历史；复制后尽快粘贴 |
| R3 | 锁屏前的窗口期：解锁状态下离开电脑 | 中 | 已提供空闲自动锁定（默认 10 分钟）+ Win+L 联动；可调更短 |
| R4 | 主密码遗忘 = 数据永久不可恢复（无后门） | 按设计 | 主密码写进纸质应急卡，存放在保险处 |
| R5 | 恶意软件同权限读取（键盘记录/内存读取） | 环境性 | 保持系统干净是前提；此类攻击者面前无本地方案可解 |
| R6 | 解析恶意构造的 .kdbx 时库/解析器崩溃 | 低 | 只读拒绝 + 不写回；依赖无已知 CVE（pip-audit 2026-10-24） |
| R7 | PyKeePass 使用 GPL-3.0；公开分发程序前须处理对应源码与第三方许可 | 发布阻断项 | 只在准备好并授权公开对应源码及许可证材料后发布 EXE |
| R8 | ToolHub 清单与 EXE 来自同一发布源；HTTPS 和 SHA-256 无法防止发布源被攻陷后同时替换程序与哈希 | 中 | 更新前由用户确认；仅从固定 ToolHub HTTPS 源获取；后续可评估独立签名 |
