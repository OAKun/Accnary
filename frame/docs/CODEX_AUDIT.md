# Accnary 0.4.0 独立审计

日期：2026-10-24 至 2026-10-25。范围：本地源码、原有测试、隔离 KDBX、Qt 桌面及独立 EXE。所有凭据均为虚构。本文不是第三方渗透测试、密码学认证或生产安全认证。

## 结论

原有 **128 项测试独立重跑通过**，但新增的第一批 21 项针对性用例在原实现上有 **18 项失败**。确实存在恢复中断损坏目标、保存竞态、锁定残留解密对象、未来 Schema 拒写失效和编辑丢失元数据等问题。不能沿用“128 项通过，所以已经安全”的结论。

本轮针对性修复后，完整回归 **172 通过、0 失败、0 错误、0 跳过**，包含原有 128 项与新增 44 项。完成实际 EXE 的录入、长网址搜索、编辑、加密备份、恢复、回收站、复制、锁定/解锁、普通最小化和关闭验证。独立产物见 `../audit/validation/dist/`；正式 release 没有被本次 Codex 构建覆盖。

结论是：**本轮工程与功能回归通过，继续作为测试版；生产安全验收不予作出。** 未合作的外部写入、真实断电、托管内存及部分扩展元数据的边界见下文。

## 实际架构

`main.py` 创建 QApplication、解锁对话框和 MainWindow。UI 调用 CatalogService；后者维护 Service、Account、LoginMethod、Identity、License 的内存对象，并映射到 KDBX 分组、标准条目字段和 `Accnary.Meta`。KdbxVault 负责凭据、格式守卫、文件验证与替换；加密仍由 PyKeePass/原依赖完成。

QQ、微信既可作为普通账号记录保存，也可作为其他账号显式引用的 Identity；不自动把二者合并。搜索只使用解锁后的内存索引。配置只保存路径与非敏感偏好，使用 INI，无新增明文账号数据库。

同目录暂存与快照始终是加密 KDBX；`.lock` 是只含零字节的协调文件，持久存在不代表后台进程。新建库使用 Windows 不覆盖已有目标的 rename；解锁摘要来自实际解密的同一份密文字节，避免“读了旧内容，却记录新摘要”。

## 测试质量判断

原测试并非全部过度 Mock：存在真实临时 KDBX 保存、重开、错误主密码、KeePassXC CLI 双向读写、历史与附件验证，具有价值。

不足在于：并发只测串行的过期实例；磁盘满在写入前直接抛错；恢复没测部分复制；原生事件仅测失败退化；GUI 多数直接调用 Python 方法；泄露错误测试自行构造安全异常；还存在一条 `... or True` 的无效断言。已移除无效断言，并补上实际进程、实际文件占用及真实 UI 场景，但不能因此声称完全覆盖所有错误路径。

全部模块一次性交给 `Pex.run()`，自动选择 worker；每个模块使用独立临时目录和 INI。模块内共享 Qt 对象、迁移状态和顺序流程保持串行。原始基线另作完整单进程执行以检查顺序依赖。

## 密码学与兼容性

- 实测保持 KDBX 4.0 / AES-256 / Argon2d，原模板 M=64 MiB、P=2、V=19、I=14；没有切换算法或调参，没有自行实现加密。
- KDBX 3.1 可读拒写、4.1 合成兼容守卫、Schema 迁移及未来版本拒写均通过。
- KeePassXC 2.8.0 CLI 的两个双向读写回归通过，包含整库由 KeePassXC 改存后再由 Accnary 重开。没有把 CLI 互操作冒充 KeePassXC GUI 属性编辑测试。
- 新增保留同版本 JSON 根扩展、按 UUID 对齐的登录方式扩展、license 扩展及注册表根扩展；用户自定义字段保留标准 KDBX 属性。
- 依赖审计重新查询了锁定的 19 个包，未报告已知漏洞；这不证明库或应用没有未知漏洞。
- KDBX 的认证与完整性机制参考 [KeePass 官方 KDBX 4 说明](https://keepass.info/help/kb/kdbx_4.html)，本地 PyKeePass 保存与临时文件行为以安装版本源码为依据。

## 残余风险与验收边界

1. **外部并发仍是生产验收限制。** OS 字节锁协调 Accnary 实例；不遵守该锁的 KeePassXC 等外部程序仍可在最后一次摘要检查与替换之间更改文件。不能宣称从理论上消除全部 TOCTOU，使用时避免多个工具同时编辑同一库。
2. **没有真实断电验证。** 已做真实进程终止、真实文件占用和部分复制故障注入；fsync/同盘替换不保证所有硬盘缓存、网络盘、云同步或存储损坏场景。没有把杀进程当成物理断电。
3. **Python/Qt 无法保证完全擦除内存。** 本轮释放本程序可控的解密引用和输入值；不可变字符串副本、allocator、交换/休眠文件、崩溃转储和第三方已取得的引用不在保证范围内。
4. **任意扩展数据不作无限兼容承诺。** 受支持 Schema 内未知枚举仍会按旧约定回落到 other/custom；未知 Binding 子字段等未定义扩展没有完整迁移协议。特殊第三方数据应先在副本做属性比对，不能把现有已测扩展外推为所有未来数据无损。
5. **自由文本可能包含秘密。** 标准密码、许可证密钥、custom field 值不进入索引；备注和 URL 按功能需求可搜索。用户手动把密码放在备注或 URL 参数中不能被自动可靠识别。
6. **主线程存储阻塞已缓解。** 解锁/创建、保存、主密码修改、备份导入导出和重读通过串行工作线程执行；锁定与退出请求会等当前任务结束。2000 条虚构账户保存约 1.675 秒时，Qt 计时器最大间隔约 23 毫秒。2026-10-26 的搜索优化保持即时响应，只跳过输入时不变的导航重建；身份 UUID 检索也改成映射查找。账户列表仍在 UI 线程重建，长列表耗时尚未测量。
7. 未签名、未经第三方独立安全审计。当前 `build_exe.py` 在构建及 promote 前检查本项目运行中的 Accnary；发现实例时拒绝继续，不会终止它。真实窗口 smoke 只清理本次脚本启动且可确认路径属于 staging EXE 的测试进程。该脚本已用于本轮构建与 promote。

这些边界使本轮不授予“生产级绝对安全”结论。暂不迁入重要真实凭据，尤其不要依赖多软件并发编辑或不受支持的扩展格式。
