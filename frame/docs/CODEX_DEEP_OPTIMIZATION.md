# Accnary 0.4.0 深度优化与复核记录

日期：2026-10-25  
范围：源码体验、解锁/退出周边、内存查询路径、隔离 GUI 实测与回归验证。

## 结论

在未改变 KDBX 格式、加密策略、主密码方案和账户模型的前提下，完成了几项针对已观察到问题的局部改进。全量自动化测试 **207 项通过**。测试只使用虚构数据和临时 KDBX；没有打开或修改真实密码库。

## 本轮处理

### 复制凭据不再立即重写整个密码库

此前复制账号或密码后，记录“最近使用”会立即调用整库安全保存流程。对 KDBX 而言，这让一次简单复制同步执行临时加密文件写入、重开校验、快照及原子替换，造成明显等待。

现在复制成功后只更新当前解锁会话中的最近使用时间；锁定或退出时已有的安全保存流程会将它一并持久化。最近使用仍会保存，凭据复制不依赖这项尽力而为的记录操作。

### 解锁会话内的 UUID 查询索引

`CatalogService` 现在在解锁会话内缓存条目 UUID、服务组 UUID、服务组名称和服务名称的查找映射，减少账户写入时重复遍历整棵 KDBX 树。映射不写入磁盘；锁定时清空，事务回滚后重建。原有保存验证和替换流程保持不变。

同一虚构 2,000 账户场景的分段测量：

| 指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 添加 2,000 个账户 | 21.26 秒 | 12.19 秒 |
| 整库安全保存 | 32.05 秒 | 1.85 秒 |
| 两段合计 | 53.31 秒 | 14.05 秒 |
| 20 次搜索平均 | 约 5.35 毫秒/次 | 搜索算法未改 |

计时包含本机 Python、PyKeePass、加密参数和临时文件系统的影响；该结果用于同机同场景前后比较，不代表所有硬件上的绝对耗时。PyKeePass 新建条目自身仍有重复性检查成本，所以添加阶段仍有优化空间。

### 空状态、回收站与解锁路径

- 详情区在未选择账户或搜索无结果时居中显示提示，减少“顶部两行文字、其余大片空白”的失衡感。
- 回收站为空时提供明确说明，恢复按钮只在选中可恢复记录时启用；主按钮禁用时也改为低对比度样式，避免看起来仍可点击。
- 解锁页的库路径字段支持清空，完整路径可通过悬停提示查看。
- 许可证的购买日期与有效期字段现在有持续可见的独立标签，已有日期值时也不会失去含义。
- `--smoke` 检查将临时 KDBX 和设置限定在临时目录，结束时关闭窗口、锁库并清理目录。

## 尚未解决/明确边界

1. 解锁和最终安全保存仍在 UI 线程同步执行。2,000 账户保存场景已显著缩短到约 1.85 秒，但更大库或较慢磁盘上仍可能让窗口短暂停顿；本轮没有引入可能改变会话生命周期的后台线程改造。
2. Python 管理的密码字符串可能存在多个运行时副本，不能保证像手动管理内存那样彻底擦除。这是现有 Python/Qt 架构的限制。
3. 本轮故障回归是软件级模拟和自动化文件操作，不等同于真实断电测试；独立第三方安全审计仍未完成。
4. 2000 账户性能数据来自虚构样本和当前机器，只说明该环境的前后变化；没有对真实用户库作任何性能探测。
5. 本次构建仍是 Accnary 0.4.0 测试版；尚未完成独立第三方安全审计或代码签名。

## 后续建议

1. 如果实际库增长后仍感到卡顿，再单独设计“解锁/保存期间可取消或显示进度”的线程化方案，并覆盖窗口关闭、锁定与取消时序。
2. 在使用真实凭据前，继续完成密码库备份恢复演练并安排独立安全审计；不要把本轮回归结果当作第三方安全认证。
